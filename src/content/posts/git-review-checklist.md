## 先看这次改动涉及哪些文件

提交之前，可以先用一句话描述目标，例如“修正文章列表的日期显示”。随后运行下面的三条命令，按文件范围、工作区差异和暂存区差异的顺序阅读输出。这个顺序能帮助发现与目标无关的文件，也能避免把工作区里的最终状态误认为即将提交的状态。

```sh
git status
git diff
git diff --staged
```

`git status` 会列出文件状态。先留意是否出现意外删除、临时文件或不熟悉的文件名，再区分已经暂存、尚未暂存和未跟踪的文件。同一个文件可能同时出现在已暂存和未暂存的部分，这意味着暂存之后又发生了修改，下一次提交不会自动包含后续编辑。

## 分别阅读两份差异

`git diff` 展示工作区相对暂存区的改动。检查这些修改是否都与当前目标有关，是否留下调试输出，以及注释是否仍然准确。如果命令没有输出，只能说明没有这类差异，不能据此判断没有其他待处理文件。

`git diff --staged` 展示暂存区相对当前提交的改动，是确认下一次提交内容的重要依据。应逐段阅读新增和删除的内容，特别留意配置、依赖文件与看似无关的格式变化。若发现问题，先修正并按需重新暂存，然后再次检查这份差异。

### 留意差异输出看不到的内容

这两条差异命令默认不会展示未跟踪文件的正文。新文件即使已经出现在状态列表里，也需要单独打开检查。图片等二进制文件同样不能只靠文本差异判断，应确认文件本身是否正确。文件数量很多时，先确认每个文件为何需要参与这次提交，再处理具体内容。

## 用目标检查提交边界

最后再运行一次 `git status`，确认已暂存的文件与目标一致，其余变化也都有明确去向。检查差异不能证明程序一定正确，还应完成与改动相符的验证，例如预览页面或执行相关测试。理想的提交应该能够用一句话解释，也能从差异中直接看出这句话对应的修改。
